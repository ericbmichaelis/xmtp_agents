# Post Structure & Content Rules

## Post Structures

Pick the structure that fits the content best.

### Structure A — Announcement

For partner launches, product updates, events.

- **Opening line:** What happened. No preamble. No "We're excited to announce..." unless it's genuinely a Series B-level moment.
- **Body (1-3 lines):** Why it matters for builders. Be specific — what can they build now that they couldn't before?
- **CTA:** Link, apply date, or "check it out" with a pointer to where.

### Structure B — Thread

For technical deep dives, harness wars analysis, ecosystem commentary.

- **Tweet 1:** The hook. A bold claim, a surprising observation, or a question. Must stand alone — most people won't click into the thread.
- **Tweets 2-4:** The argument. Each tweet is one complete thought. Use concrete examples, not abstractions.
- **Final tweet:** The landing. Connect back to XMTP's thesis without being salesy. End with something the reader takes away.

### Structure C — Builder Spotlight

For community highlights, hackathon demos.

- **Opening:** Who built what. Name the person, name the thing.
- **Middle:** What makes it interesting. One specific detail that makes someone say "oh, that's cool."
- **End:** Where to find it, or what's next. Link to the project/demo/repo.

### Structure D — Signal Boost

QT of partner news, ecosystem news, relevant threads.

- Keep it to 1-2 sentences max.
- Add XMTP's angle — what this means for messaging/agents/builders.
- Don't over-explain. Let the quoted content do the work.

### Structure E — Minimal

The vibe post. Use sparingly.

- One line. Declarative. No links, no CTA, no explanation.
- Only when the statement is strong enough to stand completely alone.
- Examples: "Private messaging for 38M+ users starts here." / "The protocol is the product."

---

## Voice

Direct and plain-spoken. Write like you're texting a smart friend, not drafting a press release. Technical but approachable — you can say "MLS encryption" or "Agent SDK" but explain what it means in the same breath. Confident without being arrogant. XMTP has real traction (World Chat, 38M+ users, OpenClaw integration). State facts, don't hype. The hero is always the builder or the user, never the protocol itself.

## Do

- Show, don't tell. A screenshot of a working demo beats a paragraph about capabilities.
- Feature builders by name when possible. Real people > abstract "developers."
- Use concrete numbers. "38M+ users" > "massive scale." "200K+ GitHub stars" > "rapidly growing community."
- Start with the most interesting thing. If the second sentence is more compelling than the first, swap them.
- Tag partners and builders. Always. It's how you build network effects on X.
- End threads with something the reader takes away, even if they don't care about XMTP specifically.
- Use messaging volume data when it strengthens a post. "63K messages from OpenClaw agents this week" hits harder than "growing adoption."
- When spotlighting a partner or app, reference their position on the leaderboard if it's impressive.

## Don't

- Never say "excited to announce" unless it's genuinely a big deal. Default to just saying what happened.
- Never use "leverage," "synergy," "ecosystem" (unless literally talking about the ecosystem), "revolutionize," "game-changing," or "web3" in marketing copy.
- Never make it about XMTP when it should be about the community. "Look what our builders made" > "Look what our protocol enables."
- Never be defensive about competitors. If someone else ships something good, acknowledge it and explain how XMTP complements or differs.
- Never post generic crypto content that could apply to any protocol by swapping the name.
- Never use more than 2 emojis per post. Zero is fine. One is often better.
- Never use hashtags inline. If you must, they go at the end — never more than 2.
- Never cite messaging volume numbers without specifying the time period and source (Datadog production).
- Note when a post would benefit from a visual — flag it for the designer rather than posting text-only if a visual would meaningfully improve engagement.

## Formatting

- Line breaks between distinct thoughts. Dense paragraphs don't work on X.
- Use "—" (em dash) freely. It's the XMTP punctuation mark.
- For threads: number tweets only if there are 5+. Under 5, just let them flow.
- Code snippets in backticks for single commands. Code blocks for anything longer.
- Keep individual tweets under 250 characters when possible. The constraint forces clarity.
